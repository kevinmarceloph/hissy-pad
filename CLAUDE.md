# CLAUDE.md (hissy-pad)

Guidance for Claude Code in this repo. The shared rules (who Kevin is, writing voice, facts bank) are in `../CLAUDE.md`.

## What this is

HissyPad: a freeform outline, always open, between Google Docs and Hissycal; since 2026-11-02 a few of them ("pads", tabs under the title, with a two-pane Fresh start that moves the leftovers of a pad into a new one). A flat `nodes` table, offline-first, each row synced on its own with last-write-wins on the server. A pad is a root-level row with `pad` set. Since 2026-11-24 the tabs start with three fixed ones: Today, Inbox and Later. Inbox is the root level itself (the old Main); Today and Later are ordinary pad rows found by name. After load and every sync merge the store makes a missing Today or Later, folds a duplicate into the first, and folds any pad named Inbox into the root (`settleFixedPads` in core, `settleFixed` in the store). Tests share `tableShape` (`state/testing.ts`), which leaves out an empty Today and Later; the store shows one pad at a time as a scoped view (`rows`) over the whole table (`all`), see `packages/core/src/pads.ts`. Web (Vite + React 19, PWA) and mobile (Expo) share the same core and state packages. Live at https://hissypad.marcelo.ph (Render static site, auto-deploys from `main`, hosted Supabase behind it). Public repo `kevinmarceloph/hissy-pad`, Kevin's first public one: nothing under NDA, no pad content, no keys.

Since 2026-11-23 it also holds **Hours**: Oras-oras (the hourly self-tracker in `../oras`, left as it is) rebuilt on this stack as a mode of its own, like Sort. One row per hour (a pad of the lines put in it; its title and state are its first line's), categories, recurring plans, a day start, chimes (flags are hidden for now); plus two things Oras-oras does not have: a line of the pad can be put in an hour of a day (`slot` on the row), and each hour lists the lines crossed out while it ran. See "Hours" below.

- `README.md`: layout, run commands, keys. Read it first.
- `docs/MAP.md`: where everything is, file by file, and where each kind of change goes (a toolbar action, an op, a column, a panel). Keep it current when a file is added, moved or removed.
- `PLAN.md`: the design (data model, sync, editing model), phases and what is pending. Keep its status line and phase notes current when a phase moves; dates are absolute (`2026-10-29`), Manila time.

## Layout

```
packages/core    pure TS, no React: types, tree, ops, rank, drop resolver, paste, pads (scoped view, fresh start), clock, sync engine, LocalStore
packages/state   Zustand store (all rows + the scoped pad), history, selection, commands, the toolbar registry (actions.ts), pads, lists, sort, shake, sync binding, Supabase remote, debug log
packages/ui      screens written once in React Native and drawn by both apps (the web through react-native-web): the Hours mode and the hour picker
apps/web         Vite SPA on :5180: src/app (shell), src/pad (editor, drag), src/pads (tabs, fresh start), src/panels (trash, done, sort), src/platform (IndexedDB, clipboard); Playwright e2e
apps/mobile      Expo SDK 58 shell: expo-sqlite store, screens in src/ui, the same toolbar registry, EAS build/update profiles
supabase/        migrations (nodes, RLS, LWW trigger), pgTAP tests, functions (watch-token: the watch's sign-in), local stack on ports 54421-54429
```

Platform logic goes in `packages/state` or `packages/core`, never in an app. If web and mobile would both need it, it belongs in a package. A toolbar button is an entry in `LINE_ACTIONS` (`packages/state/src/actions.ts`), not markup in either app. Both toolbars draw `lineActions(can)`; an action that belongs only in an open hour in Hours (or only outside one) says so with `offered` and `can.hour`.

## Hours

- Where it lives: `packages/core/src/hours` (pure logic, imported as `@hissypad/core/hours`), `packages/state/src/hours` (stores, the sync engine for its four tables and its settings, the slot commands; `@hissypad/state/hours`), `packages/ui/src/hours` (the screens). The names stay out of the pad's index files on purpose: `Entry`, `MemoryStore`, `syncLine` and others would collide.
- The code came from `../oras` on 2026-11-23 and keeps its style (semicolons, its comments). Its rules still hold and are in `../oras/CLAUDE.md`: `(day, hour)` is the calendar slot, never the day as drawn; `byHour` is what is stored and what `drawHours` returns is what is drawn; flags (hidden since 2026-11-27) are read and written through `flagChoice` and `setFlagChoice`; a color is a palette key, never a hex; nothing rests on color alone (Kevin is a deuteranope). The `hold` handlers are gone here: nothing in an open hour is a draft, every change is written as it is made.
- Hours is a focus screen since 2026-11-27 (Kevin, round 4; details in `PLAN.md` under "Hours as a focus screen, round 4"): the mode opens on one hour, the one the clock is in, alone on the screen (`FocusScreen` in `packages/ui`). Its hour line leads to the list of a day's hours (`DayScreen`, where a tap on an hour comes back on that hour; no hour opens in the list any more), then the hour's pad and foot (`HostedLines`), the hours before and after, and the ways to Today's two sections: Unscheduled (its own lines, pins included; the count leaves the pins out) and Schedule (its lines with an hour). Those two are views of the store like an open hour: `partId` (`openPart`, `scopeTodayPart` in `core/schedule.ts`), drawn by the host's pad editor through the same `renderLines` (`PartLines`). They are Today's real rows with the other section left out, so an edit goes back under Today as a pad's does; `fitOwnPart` keeps a line added at the end of Unscheduled out of the Scheduled section. Check `partId` wherever `slotId` is checked for "the store's rows are something Hours is drawing" (the phone's `Pad.tsx` does).
- The hour view since 2026-11-27 (Kevin, round 3; details in `PLAN.md` under "The hour view, round 3"): an open hour is a pad scoped to it and nothing else. The hour has nothing of its own to set: no state, no summary, no category, no flags. Its row shows its first line (`hourShown`: the words, the category and the state are that line's, so first item done = hour done), `1/3` for its own lines done out of all when it has two or more (`+N` is for a line's sub items), and `✕N` for the lines crossed out while it ran that were not put in it (`slotDoneElsewhere`, behind a text toggle in the open hour, each drawn like a hit in Search: `lineHit`, `hitNote`, `hitKids` in `state/search.ts`, so change the two together). A summary or a category for an hour is a line typed into it. `hour_entries` rows are not written from the screen any more: `note`, `category` and `state` are read only for an hour with no lines (what was typed before that day), then the recurring plan that covers it, read when drawn and never pinned (`pinRecurring`, `planned` and `plannedNote` are gone from the code, and the two columns from the server since the same day). Flags are hidden, not deleted: the store, `FlagsScreen` and the table stay for a later version. A chime's reply is a line in its hour (`cmdSlotAdd`).
- An open hour's lines are drawn by each app's own pad editor, not by these screens: `HostedLines` asks the store to show the hour (`openSlot`, `scopeSlot`; `apply` writes the rows back to the pads they live in through `unscopeSlot`) and draws what the host handed `HoursApp` as `renderLines` (`<Pad embedded />` on the web, `SubRows` with `slot` on the phone). So a change to how a line looks or edits in an hour is a change to the pad. Under the lines: empty space that takes a tap for a new line (`cmdAppendAtEnd`; a line typed into an hour goes to Today, `unscopeSlot`), a search button that opens the app's Search for this hour (`cmdFindForSlot`, `setSlotFinder`), Fresh start (`cmdSlotFresh`: the lines not crossed out leave the hour with `fresh` set, the dot of a line that came back) and Close. The count is at the foot of the open hour. An hour keeps no order of its own: its lines go by pad, then down the pad (`lineOrder`). Moving one of its own lines up or down moves it in its pad, past the hour's other lines that share its parent there (`unscopeSlot`); it cannot pass a line of another pad, and the toolbar's arrows are off for that (`lineAbilities`).
- An archived line stays in its hour, where it was in its pad (`slotShown` in `core/slot.ts`): the hour is read from a table in which its archived lines are alive, so `slotLines`, `slotTops` and the view hold them, and `scopeSlot(...).archived` says which rows they are. Each app's `Row` draws those with an archived mark at the right, which brings the line back in place, as done as it was (`cmdSlotUnarchive`). `unscopeSlot` keeps such a row archived whatever an op did to it, and archives a live line put under one. Anything new that reads an hour's lines and needs live ones only has to check `deletedAt` itself (the widget does).
- Nothing is seeded (Kevin, 2026-11-23): no default categories, no default flags. `SAMPLE_CATEGORIES` and `SAMPLE_FLAGS` exist for tests only. A new flag still starts with Yes and No as its options.
- Storage: the four hours tables are real tables on the server (`hour_entries`, `hour_categories`, `hour_flags`, `recurring_plans`, plus `hour_settings` for the day start and the chime minutes, one row per key; `updated_at` in ms as a bigint, no `deleted_at`). Settings that follow the account go in `hour_settings` through `HoursStore.putSetting`, not in the device's meta. On a device they are JSON rows behind `HoursBackend` (`core/hours/store.ts`): one IndexedDB store on web, one SQLite table on the phone. `HoursStore` keeps them all in memory and writes through.
- Sync: a second engine beside the pad's (`state/hours/engine.ts`), started and stopped by the same `bindAuth`. One sign-in, the pad's. `refresh()` syncs both.
- A line in an hour: `NodeRow.slot` is `'YYYY-MM-DDTHH'` (`core/slot.ts`; `+N` after it for a run of hours, and commas between runs for hours that are apart, so read it through `slotHours`, `slotCovers` and `slotRuns`, never by hand), set by the toolbar's "Hour…" (`LINE_ACTIONS`, a clock icon on the toolbar of both apps; it opens the shared `SlotPicker` through `setSlotPickerOpener`) or by typing a line into an open hour, or by marking it doing, which adds the hour it is now (`slotDoingHour`, through `doingState`; done does not). Counts are `slotCounts` over the whole table: every pad, blank lines and pad rows left out, a line counted for itself only.
- On the phone Hours has no menu of its own and its screens start with the app's name (`brand` on `HoursApp`, `useBrand()` in `packages/ui/src/hours/host.tsx`): a new Hours screen draws its first row as the name at the left and its own control at the right when `useBrand()` gives one, and anything that used to be in Hours' menu goes in the phone's `MenuScreen.tsx` too.
- Web and phone differ in a few wired-up things (chimes, pull to sync, what was checked by hand): the table is in `PLAN.md` under "Hours". Keep it current when one side catches up.
- Chimes: the web rings from the page (`apps/web/src/platform/chimes.ts`); the phone uses local notifications (`apps/mobile/src/chimes.ts`, expo-notifications, loaded only when the build has it).
- The web app aliases `react-native` to `react-native-web` and dedupes `react` (`vite.config.ts`, `vitest.config.ts`). Hours is loaded on first use (`apps/web/src/panels/Hours.tsx`), so the pad does not carry it.

## Boomerang

Since 2026-11-25 a line can be sent out of the pads until a later day (the floating Boomerang button). Details in `PLAN.md` under "Boomerang"; the rules that bite:

- A line that is out has `due` ('YYYY-MM-DD') and sits under the Later pad row. `scopePad` and `padLines` skip a row with `due`, so anything built on them leaves it out for free; anything that walks `all` or `childrenOf(index, later)` itself has to skip it by hand.
- Later's own view is the exception (2026-11-26): the store shows Later through `scopePad(all, id, true)` (`padView`), so the lines that are out are rows of the pad, under Later's own lines, in groups by day, and every pad command works on them. The groups are kept by rank, not by the drawing: `settleBoomerangs` (core, run by `commit` and `settleFixed` like `settlePins`) holds Later's own lines first, then the days in order, puts a line dragged out of its day back at that day's near edge, gives a new line in a group that group's day, and takes `due` off a line that is no longer a top-level line of Later. The day headings are drawn from `dueHeads`. An op that adds a line "at the end" of a pad has to mean the end of its own lines (`cmdAppendAtEnd`).
- Delivery (`deliverBoomerangs`) puts a line at the top of Later's own lines (since 2026-11-27; the Inbox before), as does Back now (`comeBack`). It is not an edit: it goes through `applyQuiet`, with no undo step, and stamps the row with the moment its day started (not now), so a device that wakes up late does not overwrite newer edits. Keep that stamp if the delivery changes.
- A day here is Hours' day: it starts at the day start setting, read from the hours stores (`openHours().day`).
- `fresh` (the dot on a line that came back) is cleared by `commit` on any edit to the row.
- The watch does not know `due` yet.

## Recurring items

Since 2026-11-27 a line can be made a recurring item from the hour picker's Repeat section (two kinds: on a schedule, or so long after the last was done). Details in `PLAN.md` under "Recurring items"; the rules that bite:

- The template is a row under Later with `repeat` (the rule, JSON: read and write it through `parseRepeat` and `formatRepeat`, never by hand) and `due` set to `FOREVER` ('9999-12-31'). It is a boomerang that never comes back, so `isBoomeranged` is true for it and whatever skips `due` skips it. Anything that reads `due` as a real day has to leave `FOREVER` out (`targetDue`, the delivery's timer and `dueLabel` do).
- An instance has `origin`, the template's id. Whether a row is a template or a live instance of one is `repeatLink`; an `origin` whose template is gone or has stopped means nothing.
- `settleRepeats` runs before `settleBoomerangs` in `commit` and `settleFixed`: a template anywhere but the top level of Later loses its rule. The template is in no hour: its instances' hours are in the rule (`cmdSetSlot` and `targetSlot` know).
- The delivery (`deliverRepeats`, run by `deliverBoomerangs` through `applyQuiet`) must write the same rows on every device: ids from `derivedId(templateRowId, day)`, stamps from the moment the day started, nothing made twice. Keep all three if it changes. Instances land at the top of Today.
- The watch does not know `repeat` or `origin`.

## Today's Scheduled section

Since 2026-11-27 Today's top-level lines with an hour sit under its own lines, below a "Scheduled" heading, always in the order of their hours (`settleSchedule` in `core/schedule.ts`, run by `commit` and `settleFixed` like `settleBoomerangs`). It is kept by rank, not by the drawing. A new line in the section takes the hour of the line above it, so an op that adds a line "at the end" of a pad has to mean the end of its own lines (`lastOwn` in the store). Details in `PLAN.md` under "Today's Scheduled section".

## Category views

Since 2026-11-27 Categories is a mode of its own, between Pad and Sort (the tag icon; first a dropdown in the row of pads, a mode the same day). Under the top bar is a centered dropdown of the categories, with "No category" last (the lines that have none: `NO_CATEGORY` in place of a category's id), and the open one is shown in place of the pad: its lines from every pad, in groups by pad, with the lines over and under them whatever their category (`catId` in the store, `scopeCategory` and `unscopeCategory` in `core/category.ts`). It is a view like an open hour: the pad's editor draws it and every pad command works in it. A line in it can have siblings the view leaves out, so anything new that acts on "everything under a line" from `rows` has to mean the table's (archiving does: `unscopeCategory`). Rows show no category icon there, only the colored bullet. An existing line moved to where the view would stop holding it takes the category (`unscopeCategory`), and under each pad's group an add area (`CategoryAdd`, placed by `categoryTails`) makes a line in that pad and category. `categoryShown()` says whether it is on screen as itself (not under a zoom or an open hour); check it wherever `slotId` is checked for "this is not a pad as itself". Each app opens a category on the way into the mode (`cmdOpenCategories`: the one it had last) and closes it on the way out (`closeCategory`); `openPad` ends it, and the apps follow that to the Pad mode (a subscription on `catId` in `App.tsx` and the phone's `Pad.tsx`). Details in `PLAN.md` under "Category views".

## Section dividers

Since 2026-11-27 a line can be a section divider (`divider` on the row, the fourth type in `LINE_KINDS`): a rule with its text centered and gray. It never has lines under it and is never done or counted. `setKind` kicks the sub items out; `moveNodes`, `indent`, `resolveDrop` and `insertOutline` refuse to put a line under one, so a new op that gives a line a parent has to go through `moveNodes` or check `divider` itself. The watch does not know it yet. Details in `PLAN.md` under "Section dividers".

## Rules

- Work in a worktree, never in the checkout at the repo root. Sessions started from the phone over Remote Control open in `/Users/kevin/Personal/hissy-pad` itself, on `main`, with no worktree, and several of them at once would edit the same files. So if the working directory is that root (not under `.claude/worktrees/`), call `EnterWorktree` with a short name for the task before editing any file; a read-only question needs none. Shipping from the worktree then follows the steps below.
- A change counts as done when `pnpm test` and `pnpm typecheck` pass and, for anything visible, it was checked in the browser (or the simulator for mobile).
- Ship every done change without asking, in this order:
  1. Commit on `main` with a one-line message that says what changed, and push. Render rebuilds the web app from `main` on its own.
     From a worktree, never push the branch straight to `origin/main`: that leaves the checkout at the repo root (`/Users/kevin/Personal/hissy-pad`) behind what is live. Instead, fast-forward that checkout first (`git -C /Users/kevin/Personal/hissy-pad merge --ff-only <branch>`, after checking it is on `main` and clean), then push from it. If it will not fast-forward, say so and stop instead of forcing or rebasing it.
  2. If anything under `apps/mobile`, `packages/core` or `packages/state` changed, publish an OTA update so the phone picks it up: `cd apps/mobile && npx eas-cli update --channel preview --environment preview --message "<commit subject>" --non-interactive` (the standalone build on Kevin's iPhone is on `preview`). Publish the same to `development` when the dev client is in use.
  3. A native change (a new dependency with native code, `app.json`, `eas.json`, a config plugin, an Expo SDK bump) cannot ship as an update: run `npx eas-cli build --profile preview --platform ios --non-interactive` instead and say that the phone needs the new build installed.
  4. Watch CI (`.github/workflows/ci.yml`: typecheck, Vitest, build, Playwright e2e, pgTAP). A push is not done until the `ci` run for its commit finishes: `gh run list --commit <sha>`, then `gh run watch <id> --exit-status` (in the background; it runs a few minutes). If it fails, read `gh run view <id> --log-failed`, fix it in the same session and ship the fix the same way, even when the break is not from your change (a flaky test, a slow runner, a pinned tool). Before starting, `gh run list --limit 3` on `main`: if it is already red, fix that first or say so.
  Say in the reply what was pushed, updated or built and how CI came out, and skip a step only when its check failed, saying so.
- Schema changes are a new file in `supabase/migrations/` with a pgTAP test, plus the matching column add in the mobile SQLite store (it migrates on open). Rows are never hard-deleted; `deleted_at` is the tombstone.
- The Apple Watch app is a sync client of its own, in Swift (`apps/mobile/targets/watch`): it repeats the tree, open-line and merge rules from the packages, so change `Rows.swift` with them. Siri's add on the phone sends through the same `Remote.swift` and `Rows.swift` (`apps/mobile/native/SiriSync.swift`), compiled into the app. A change under `supabase/functions/` ships with `supabase --workdir /Users/kevin/Personal/hissy-pad functions deploy <name>`.
- Every edit stamps `updated_at` through the clock in core. Undo re-stamps the touched rows so the change syncs.
- A shared screen goes in `packages/ui`, in React Native, only if it needs nothing the DOM has and the phone lacks. The pad's editor stays per app. Its tests run in jsdom through react-native-web (`packages/ui/src/testing/rntl.ts` maps React Native Testing Library's `press` and `changeText`).
- A new column on `nodes` needs `PULL_EPOCH` raised in `core/sync/engine.ts` when it ships: a device still running the old code pulls rows that carry the column, stores them without it and moves its cursor past them (2026-11-23: the phone showed no hour chips for lines given one on the web). Under a new epoch every device reads all rows once more, and the merge takes the server's row over a clean local one of the same `updated_at` that differs. The watch's own merge (`Rows.swift`) was left strictly-newer: it only keeps columns it knows.
- The store can zoom into one line (`zoomId`, `zoomTo` in `state/store.ts`): `rows` is then what is under that line, and every command works there. The new item's card and Sort's card use it (`state/create.ts`, `state/sort.ts`). Anything that must see the pad while zoomed reads `scopePad(all, padId)` (`sortRows`), not `rows`. While zoomed, only one set of pad rows may be on screen: the web unmounts the pad behind the dialog, the phone's pad screen keeps the rows it last had, with nothing being edited. A write to the zoomed line itself goes through `applyAll`.
- `_repro.test.*` files are scratch reproductions, not part of the suite. Delete them when the bug is fixed.
- Keep the look: paper ground, serif, one accent. Dials in the header of `apps/web/src/styles.css`. The colors and text sizes are one set for the web, the phone and Hours: `packages/core/src/look.ts` (the stylesheet repeats them and `apps/web/src/look.test.ts` holds it to them), so change them there and in the stylesheet together.

## Gotchas

- `pnpm --filter @hissypad/web e2e` reuses whatever answers on port 5181. Another session's dev server there means the tests run against that session's code, not yours: copy `playwright.config.ts` with another port and `reuseExistingServer: false` and run `playwright test -c` on the copy.
- Metro started with `CI=1` does not watch files: it keeps serving the first bundle. Start it without `CI`, with stdin from `/dev/null`.
- A line is 25.5px (17px * 1.5) on the web and 26pt on a phone; the numbers are in `packages/core/src/look.ts`, which the phone's theme and Hours' import and a test holds the stylesheet to. Anything that copies a rounded `scrollHeight` or `offsetHeight` into a height will be half a pixel off; snap to whole line-heights (see the textarea auto-grow in `apps/web/src/pad/Row.tsx`).
- Android (started 2026-11-25, see `PLAN.md` under "Android"): builds need `JAVA_HOME` set to Android Studio's JDK (`/Applications/Android Studio.app/Contents/jbr/Contents/Home`) and `ANDROID_HOME=~/Library/Android/sdk`. Android's TextInput ignores `lineHeight` in its own style; give it a Text child that carries it (`Row.tsx`). A list of choices or a question on the phone goes through `menu()` and `askText()` (`apps/mobile/src/ui/Menu.tsx`), never `Alert.alert` with more than three buttons or `Alert.prompt`: Android cuts the first and lacks the second. A new full-screen `Modal` starts with the `SHEET_TOP` strip. The Oppo is 360pt wide: check a new row of buttons at that width (`adb shell wm density 480` on the emulator, `reset` after). The debug build reloads on two r's typed in a row, and `expo run:android --variant release` installs on every connected device, the emulator included. The Oppo A92 runs the EAS `preview` build, so step 2 of shipping reaches it as it does the iPhone; a native change (step 3) needs `--platform android` built and installed as well (`adb install` the APK).
- The bullet is also the drag handle: its tap target grows sideways only, never up or down, or the row below steals the tap.
